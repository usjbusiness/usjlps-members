LPS MEMBER PORTAL — ТЕСТОВЫЙ ПАТЧ: ВХОД + ЛИЧНАЯ НЕДЕЛЯ

ОСНОВА
Патч подготовлен поверх архива LPS-Member-Portal-Design-Only.zip, который был передан ранее. Если после него код сайта менялся, сравните файлы и перенесите изменения вручную. Сначала сделайте резервную копию кода и базы. Не добавляйте этот патч в production до проверки безопасности и реальных сценариев ниже: сервер, письма и E-Board не были протестированы в рабочей среде.

ФАЙЛЫ
Сохранены пути относительно корня проекта. Кроме этого файла README в архиве только новые и изменённые исходники и одна новая SQL-миграция. Пароли E-Board и политики E-Board этот патч не меняет.

ЧТО ИЗМЕНИЛОСЬ
• Вход по паролю или существующему коду на email. После входа по коду предложено установить пароль; установка/смена в профиле — с повторной проверкой по email; восстановление — по письму. Если оба портала используют одну запись пользователя в одном Supabase Auth, пароль общий и смена действует в обоих. Одинаковый email сам по себе не гарантирует общего аккаунта.
• Выбор Keep me signed in сохраняет сессию на устройстве с автообновлением токенов. При отключении профиль переносит сессию в sessionStorage. Срок фактического входа ограничивают политики Supabase, браузера, отзыв и истечение токенов. Это не бессрочная гарантия. На чужих/общих устройствах опцию надо выключать.
• My Week: день и неделя (Eastern Time), собственные разовые и еженедельные дела, начало и конец, место, редактирование и удаление, с повторением до даты или бессрочно. Изменение повторяющейся записи меняет всю серию; исключения для отдельного дня не поддерживаются. Записи загружаются и сохраняются в личной таблице, не обещается офлайн-сохранение. При недоступности таблицы отображается ошибка, сохранение недоступно.
• Слои LPS и курсов можно выключать. LPS берутся из существующего member_events; отменённые/завершённые исключаются, tentative отмечаются, отсутствие времени окончания подписано. Мероприятия через полночь отображаются только в день начала. Доступность будущих/прошедших событий зависит от существующей функции сервера. Курсы — включённые курсы активного плана на устройстве; если не заданы даты семестра, повторяются каждую неделю. Существующий Course Planner не перезаписан и работает по своим правилам синхронизации: сохраняйте/загружайте его копию отдельно. Это не официальный календарь регистрации или проверка наличия мест.
• Защита личных записей: SQL создаёт таблицу с owner-based RLS. Администраторы БД/роли с bypass RLS могут видеть данные. Проверка реальных политик и тесты изоляции не проведены.

НАСТРОЙКА И УСТАНОВКА В ТЕСТОВОЙ СРЕДЕ
1. Для безопасной проверки нужен отдельный тестовый Supabase-проект с совместимыми таблицами, RPC, Edge Function super-handler и тестовыми пользователями. Пустая копия фронтенда с production Supabase — НЕ изолированный тест. Скопируйте файлы патча с сохранением путей; npm ci, npm run build. В переменных среды используйте только public/publishable или anon ключ, никогда service-role на фронтенде.
2. Проверьте и выполните supabase/migrations/20261109000100_member_weekly_items.sql на тестовом проекте. Эта миграция не запускалась нами. Проверьте, что таблица не конфликтует с существующей схемой и что у неё нет дополнительных разрешающих политик/доступов. Существующие миграции повторно не запускайте без анализа.
3. В тестовом Supabase включите email/password sign-in; настройте SMTP/шаблоны существующего входа и восстановления. В Authentication → URL Configuration разрешите точный URL https://<ваш-тестовый-домен>/reset-password и проверьте, что он входит в разрешённый список. Восстановление реализовано для implicit-ссылки с #type=recovery, access_token и refresh_token; PKCE или шаблон, содержащий только код, потребуют отдельной доработки. Если включена Secure password change и сервер требует nonce, проверьте и при необходимости доработайте этот сценарий. Не присылайте пароли и коды в чат.
4. Проверьте вход по коду и паролю, предложение установить пароль, изменение, восстановление, истечение и повторное использование ссылки, несуществующий email, смену на двух устройствах, закрытие браузера с включённым и выключенным Keep me signed in, истечение/отзыв сессии. При общем аккаунте проверить влияние смены пароля на E-Board.
5. КРИТИЧНО: совместный Supabase Auth не даёт права на E-Board автоматически только при корректных серверных политиках. Проверить реальные RLS, RPC/security-definer, storage и Edge Functions E-Board. Тесты: анонимный пользователь, действующий рядовой член и бывший участник не должны видеть интерфейс/данные и получать доступ прямыми API-вызовами; уполномоченные роли сохраняют только нужные права. Этот патч не обеспечивает и не подтверждает защиту E-Board.
6. В тестовой БД проверьте два реальных тестовых аккаунта A и B: A не может читать, вставлять, изменять или удалять строки B даже прямыми запросами; anon не имеет доступа. Проверить сеть, закрытие/повторную загрузку страницы, многократное редактирование с двух устройств и ошибки. Проверить разные даты, переходы летнего времени и обе темы на телефоне и компьютере. Не публиковать до успешного завершения проверок и утверждения ответственного за безопасность.
